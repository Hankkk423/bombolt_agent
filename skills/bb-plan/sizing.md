# scope 判斷：這個需求能不能「一個 issue、一個 PR、一次做完」

bombolt 的前提是：**實作 session 拿到 issue 之後，不需要再問人就能做完、並且自己驗收到全綠。**
scope 太大會同時破壞這兩件事——context 被塞爆、驗收條件多到互相牽制、一個 PR 大到人看不完。

## 駁回條件（任一條成立就駁回）

| # | 條件 | 為什麼 |
|---|---|---|
| 1 | 預估改動超過 **~10 個檔**或 **~400 行**（不含自動產生的檔、lock 檔、測試快照） | 超過這個量，單一 session 的 context 開始吃緊，review 也看不完 |
| 2 | 包含**超過一條獨立可交付的功能**（拆開之後各自都有使用者看得到的價值） | 應該是兩個 PR，混在一起會讓驗收與 review 互相拖累 |
| 3 | **寫不出一句話的 PR 標題**（要用「和」「以及」連接兩件不相干的事） | 同上，這是第 2 條最快的檢查方式 |
| 4 | 有任何一條完成條件**無法機械驗證**（只能靠「感覺對了」） | 實作 session 無法自己判斷完成 |
| 5 | 需要**先做一個還沒決定的技術選型實驗**才知道怎麼做 | 那個實驗本身應該是另一個 issue（spike） |
| 6 | 依賴一件**還沒完成的事**（另一個沒 merge 的 PR、外部團隊、還沒開的權限） | 實作 session 會卡住 |

⚠️ 這些門檻是起點，不是真理。每個 PR 最後的「bombolt 回饋」會累積實際數據，之後再調。

## 邊界情況

- **剛好在門檻上**：直接問使用者（AskUserQuestion），附上你的估計與理由。
- **很小的改動**（一兩行）：仍然走完整流程，但研究與提問可以非常短——不要為了形式硬擠問題。

## 駁回時要給什麼

使用者的裁決是「**只駁回，並給建議的拆法**」（不自動開多個 issue）。駁回訊息要有：

1. **為什麼太大**：命中了哪幾條、你的估計（檔案數、行數、功能數）。
2. **建議的拆法**：拆成 2–5 個，每個都要是**可以獨立 merge、merge 之後系統仍然正常**的切片，並標出先後順序與依賴。
   優先「垂直切」（一條完整的使用者可見路徑）而不是「水平切」（先做完所有 DB、再做所有 API）。
3. **建議先做哪一個**，以及它的一句話描述——讓使用者可以直接拿它重新呼叫 `/bombolt:bb-plan`。
