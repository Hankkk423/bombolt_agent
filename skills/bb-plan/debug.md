# 排查問題

## 原則

- **先有證據再下結論**。問題不一定出在 code：使用者操作錯誤、第三方服務或網路、資料或設定錯了都很常見。
  沒有證據支持「是 code 的問題」，就不開 fix issue。
- **只讀不寫**：這個 session 在主 checkout，沒有安全守門。不改 code、不改資料、不重新部署、不對外發訊息。
  碰正式環境只用 `.claude/bombolt.md`「排查資源」一節寫的唯讀方式；那一節沒寫的，請使用者提供，不要自己找門路。
- **不在這裡修**：修正一律交給 bb-work（worktree、驗收、PR）。這裡把原因查清楚、寫進 issue。

## 1. 補齊症狀

先整理使用者已經給的資訊，缺的才問（AskUserQuestion，一輪問完）：
- 誰、在哪個畫面或功能、做了什麼操作、看到什麼、原本預期什麼
- 什麼時候開始、每次都會還是偶爾、影響一個人還是所有人
- 錯誤訊息、截圖、request id、發生的時間點（查 log 要用）

## 2. 收集證據

- **code**：在快照裡找出這個行為經過的程式路徑（大範圍的搜尋派 Explore subagent），讀懂現在的行為與錯誤處理。
- **最近的改動**：`git log origin/<base> --since=<開始發生的前幾天> -- <相關路徑>`，看是不是哪次改動造成的。
- **log、錯誤追蹤、資料**：照「排查資源」一節，只用它寫的唯讀方式。
- **第三方服務**：它的狀態頁、錯誤碼的意思（上網查）。
- **重現**：能在快照裡安全重現的就重現（例如跑一小段只讀的腳本）。要把整個 app 跑起來才能重現的不在這裡做，寫成 fix issue 實作步驟的第 1 步。

每一個假設都要有支持或排除它的證據，記下來，最後要寫進報告或 issue。

## 3. 判斷原因，照原因決定出口

| 原因 | 出口 |
|---|---|
| **程式碼的 bug** | 回到 bb-plan 第 3 步，把「修好這個 bug」當成需求繼續（排查時已經查過的不用重查；訪談、冷讀、開 issue 照常）。issue 標題的 type 用 `fix`，「🐞 問題與根因」一節照下面寫 |
| **使用者操作錯誤** | 不開 fix issue。給排查報告，附一段可以直接回給回報者的說明（怎麼操作才對） |
| **第三方服務或網路** | 不開 fix issue。給排查報告：哪個服務、什麼時候、錯誤碼、現在恢復了沒，以及處置建議 |
| **資料或設定錯了** | 不開 fix issue。報告裡列出修正步驟，**由人執行**（這個 session 不改資料、不改正式環境的設定） |
| **查不出來** | 不開 issue。報告裡列出已經排除的原因、還缺什麼資訊才能繼續（例如某個時間點的 log、重現步驟），請使用者補齊之後再跑一次 |

- 不確定是哪一種、而且答案會決定要不要改 code → 把證據給使用者看，用 AskUserQuestion 問。
- 不是程式碼的問題，但程式可以做得更好（錯誤訊息講清楚、防止誤操作、第三方失敗時重試或提示）→ 報告之後用 AskUserQuestion 問要不要開一個改善的 issue；
  要的話回到 bb-plan 第 3 步，把它當成新需求繼續。

## 4. 排查報告（不開 fix issue 時，直接回給使用者）

- **結論**：哪一種原因，一句話；信心（確定／很可能／推測）
- **證據**：看到什麼、在哪裡看到的（`path:line`、log 的時間與內容、指令輸出）
- **已經排除的**：每一條為什麼排除
- **建議處置**：誰要做什麼；要回給回報者的話

最後照 bb-plan 第 10 步第 1 點刪掉快照。

## 「🐞 問題與根因」怎麼寫（開 fix issue 時）

- **重現步驟**：照抄就能做的步驟，預期與實際的結果。
- **根因**：`path:line` 與一句話說明錯在哪裡，附上證據。
- **為什麼之前沒被抓到**：一句話（缺哪種測試、哪個情況沒想到），幫 reviewer 判斷要不要補別的測試。
- DoD 要有一條「新增的測試 `<名稱>` 重現這個問題並通過」（repo 沒有測試框架：照重現步驟實際操作代替）；
  實作步驟第 1 步寫「先寫這個測試，確認修改前會失敗」。
- 根因是推論、還沒實際重現的話，寫明，並在實作步驟第 1 步加上「修改前測試沒有失敗 → 根因不對，走停工提問」。
