# 人工測試指南怎麼寫

## 原則

- **AI 能測的先測完，人只測 AI 測不到的。** 寫進指南的每一步，verifier 都會在本機實際照做一遍，
  人拿到的是做過一遍、照抄就能做的步驟。目標是 5–10 分鐘測完。
- 「要你測的」只放這幾種：
  - 人測的環境跟 verifier 不一樣時（例如 stage：部署、設定、資料都不同），在那個環境走一次主要流程。
    跟 verifier 是同一個環境（例如就在這個 worktree 啟動）就不用，AI 已經走過了。
  - 要人判斷的：畫面看起來對不對、文案、操作順不順。
  - AI 測不到的（verifier 標 ⚠️ 的），寫出為什麼測不到。
  - 實作時自己做的判斷、issue 沒寫清楚的行為（之後會寫進「👀 請你重點看」），
    以及 `.claude/bombolt.md`「人工測試」一節寫的每次都要人看的項目。
- 其他的都放進「AI 已經測過」（邊界情況、錯誤處理、回歸通常在這裡），人不用重測。同一步也符合上面某一種的，放「要你測的」。
- **每一步都是實際操作**：在瀏覽器裡操作、呼叫 API（純後端），或像使用者一樣執行 CLI／腳本。跑測試指令屬於驗證閘門，不寫成步驟。
- **能寫成 repo 裡的自動測試的，也寫成測試**（bb-work 第 6 步），「AI 已經測過」附上測試名稱：
  自動測試擋之後的回歸，實際操作確認現在真的能用。
  照正常操作觸發不了的情況（例如外部 API 回 500；不要為了觸發它去改設定或環境）：用自動測試涵蓋（repo 有測試框架、還沒有測試的就補上），
  寫「只有自動測試：`xxx`」留在「AI 已經測過」；寫不了測試的才標 ⚠️ 放進「要你測的」。
  會真的寄信、扣款這類 verifier 不能做的，不算觸發不了，一樣標 ⚠️ 放進「要你測的」。
- **照抄就能做**：寫完整的網址或指令、點哪裡、輸入什麼值；預期結果寫畫面上會出現的字、response 的 status 與欄位，
  有副作用的寫去哪裡看（資料庫、收件匣、log），不寫「應該正常」。
- 指令、網址、帳號、識別字一律包成 inline code：`@名字`、`#數字`、`<名稱>` 不包的話，GitHub 會當成提及、issue 連結、HTML 標籤。

## 要涵蓋什麼

先全部列出來，再分成「要你測的」和「AI 已經測過」兩組：

- issue 改變的每一個行為，至少一步（對應到 DoD 的，後面標 `DoD n`）。
- issue 決定過的邊界情況（空資料、錯誤、權限、重新整理之後…），各一步。
- diff 裡其他會改變行為的地方（分支、提早 return、錯誤處理、副作用），各一步——bb-reviewer 會照這個檢查有沒有漏。
- 回歸：被改到的函式、元件、端點的其他呼叫端，各挑一個最常用的操作，確認沒有壞
  （沒有其他呼叫端的話，挑同一個函式、handler 裡沒改到的路徑）。

## 環境

照 `.claude/bombolt.md` 的「人工測試」一節寫；沒有這一節就以本機、照「啟動 app」寫。

- **stage**：第一步寫怎麼確認 stage 上已經部署了這個 PR 最新的 commit（寫出短 sha，確認的方法照設定檔），
  接著寫網址、怎麼登入。
- **本機**：人用 sandbox 開，不用自己打指令。寫：在任何一台電腦的 repo 主 checkout 開一個 Claude Code session
  （在外面：用手機的 Claude app 透過 Remote Control 連回那台電腦），說「開 sandbox <issue 編號>」（本機，`http://localhost:<port>`）
  或「開外網 sandbox <issue 編號>」（有帳密保護的臨時網址，手機也能開）。那台電腦還沒有這個 PR 的 worktree 的話，它會先從 PR 建一個；
  接著給網址與測試帳號，帶著照下面的步驟測；測完說「關掉 sandbox」。
  自己啟動的方式收進 `<details>`：在哪個目錄（照設定檔；沒寫就 `cd <worktree 路徑>`，每台電腦的 worktree 都在同一個位置）、
  啟動指令（port 之類填好實際的值）、網址、怎麼登入、怎麼關掉。
- 要先準備的資料（seed、測試帳號、token）也寫在這裡。密碼不寫，寫去哪裡拿。

步驟本身不管在哪個環境都一樣（頂多網址的主機不同），所以 verifier 可以把網址換成本機的服務照做一遍。

## 版面

`<artifacts>/test-guide.md` 的內容會直接貼在 PR 的「📋 人工測試（merge 前）」標題下面：

```markdown
> 預計 {{N}} 分鐘。「要你測的」與「AI 已經測過」除了標 ⚠️ 和「只有自動測試」的，每一步 AI 都已經在本機照做過一遍，結果跟預期一樣。

**環境：{{stage／本機}}**

1. {{…}}
2. 登入：{{帳號，密碼去哪裡拿}}

**要你測的**

- [ ] 1. {{操作}} → 應該看到 {{預期結果}}（{{為什麼要人測}}）
- [ ] 2. ⚠️ {{操作}} → 應該看到 {{預期結果}}（AI 測不到：{{原因}}）

<details>
<summary>AI 已經測過、你不用重測的（{{n}} 項）</summary>

- {{操作}} → {{實際看到的}}（{{DoD n／邊界／回歸：…／測試 `xxx`}}）

</details>

有一步不對：在 PR 留言寫「要你測的第 n 步：做了什麼、看到什麼」，再照「🔁 要修改的話」。
```

- `- [ ]` 在 GitHub 上可以直接勾，PR 列表會顯示勾了幾項。
- verifier 回報「啟動不了」：最上面那句換成原因，主要流程全部放進「要你測的」。
- verifier 回報「不適用」（改動不影響執行中的服務）：最上面那句換成原因，「要你測的」只留要人判斷的，沒有就寫「無」。
- 🚧 draft PR，或 bb-fix 驗收沒過：最上面那句改成還沒通過驗收，沒過的步驟標 ❌。

## 照做一遍之後

verifier 會回報每一步實際看到的結果（寫指南時 verifier 還沒跑，「AI 已經測過」先寫預期，這時換成實際看到的）：

- 跟預期不一樣、是 code 的問題 → 修 code（跟 DoD 沒過一樣）。
- 跟預期不一樣、但實際的結果才是對的（預期寫錯了）→ 照 verifier 看到的改，不用重跑。
- 步驟寫得不清楚、照做會卡住 → 改寫之後，再派 verifier 只照那幾步做一次。
- ⚠️ 無法驗證、原因不是 code → 移進「要你測的」，寫出 AI 為什麼測不到
  （有自動測試涵蓋、只是照正常操作觸發不了的，照上面留在「AI 已經測過」）。code 造成的算 code 的問題。

## bb-fix 更新時

整份要涵蓋整個 PR 的改動。「要你測的」裡，這一輪 bb-fix 改到的東西會影響到的步驟前面加 🔄（人只要重測這些），
上一次 bb-fix 留下的 🔄 拿掉，勾選框全部重設成沒勾。
